블로그 글을 쓸 때 쓸 재료를 모아 둔 문서다. 미션별 상세 일지는 `LOG.md`, 설계 교훈은
`docs/design-guide.md` §0, 이전 세션 대화 기록에서 뽑은 원자료(사용자 메시지 원문, 시작 과정의 분 단위
타임라인, 통계)는 `docs/transcript-notes.md`에 있다. 비행 텔레메트리는 `runs/flights/*.jsonl`(git에는
안 올라감), 스크린샷은 `docs/media/`에 있다. 새 이정표를 달성하면 여기도 갱신한다.

## 1. 한 줄 요약
Kerbal Space Program 1(1.12.5, Steam, Windows)의 **Normal 난이도 커리어**를 Claude Code가 WSL 터미널에서
직접 플레이한다. 로켓 설계, 조립, 발사, 비행, 연구, 시설 업그레이드, 계약 수락까지 모두 Claude가 한다.
사람이 준 목표는 "처음부터 시작해서 Minmus에 가고, 그다음 Mun, Duna로 점점 멀리" 하나뿐이다.
오토파일럿 모드(MechJeb 등)는 쓰지 않고, 비행 제어 코드도 Claude가 직접 작성했다.

## 2. 구조: Claude는 KSP를 어떻게 조작하나

```
Claude Code (WSL 터미널)
   │  uv run ksp <명령>      ← 명령 하나가 비행 단계 하나(ascent, transfer, land ...)
   ▼
kspbot/ (Python)            core.py 연결 · flight.py 비행 단계 · recorder.py 비행 기록기 · cli.py
   │  kRPC (TCP 127.0.0.1:50000)
   ▼
KSP 1.12.5 (Windows)
   ├─ kRPC 0.6.0 모드       : 기체 상태 읽기, 스로틀/자세/스테이징, 기동 노드, 타임워프
   └─ KspBot 모드 (직접 제작, C# ~870줄): kRPC에 없는 기능
        · CraftBuilder : JSON 명세 → .craft 파일 (VAB 조립을 코드로)
        · Service      : 기술 연구, 시설 업그레이드, 승무원 고용, 부품 목록, KSP 비행 이벤트 로그,
                         팝업 닫기, 상태 조회, (샌드박스 전용) 궤도 텔레포트
        · AutoLoad     : 메인 메뉴에서 세이브 자동 로드 (클릭 없이 게임 시작)
```

- **화면을 보고 마우스로 조작하지 않는다.** 모든 조작은 API로 한다. 화면은 확인용으로만 본다
  (`ksp shot` → 게임 스크린샷 PNG → Claude가 이미지로 읽음).
- **비행은 단계별 명령으로 한다.** `ascent --alt 80000` → `circularize` → `transfer Minmus --pe 20000` →
  `soi` → `capture` → `land` → `science` → `liftoff` → `return` → `reentry`. 각 명령은 해당 단계가 끝나야
  반환된다. 오래 걸리는 단계(전이, 재진입)는 백그라운드로 돌리고, 끝났다는 알림을 받으면 다음 단계로 넘어간다.
- **비행 기록기(recorder)**: 모든 비행 명령이 1 Hz 텔레메트리와 이벤트를 JSONL로 남긴다. 파손·폭발·과열(KSP
  비행 로그), 사라진 부품, 스테이징, 자세 이상(텀블링, 받음각 진동, 스핀)을 `!! [kind] ...` 한 줄로
  실시간 출력한다. 실패하면 이 기록부터 읽고 원인을 진단한 뒤에 코드나 설계를 고친다
  (사용자가 요청한 원칙: "고치기 전에 먼저 관측하고 기록하라").
- **비행 알고리즘은 직접 짰다.**
  - 상승: 250 m에서 피치오버를 시작하는 중력선회, 받음각 제한, 원지점 도달 예상 시간 기반 스로틀
  - 전이: 호만 전이 위상각 계산 → 기동 노드 → 목표 근지점에 맞춰 노드 성분을 좌표 하강법으로 튜닝
  - 착륙: 발 높이 기준 감속 곡선 + 피드포워드, 감속 상한 3 m/s² (시뮬레이션상 접지 속도 ~1.5 m/s)
  - 궤도 측량: 지상 궤적을 미리 계산해 계약 지점 위를 지나는 시각으로 워프한 뒤 실험 실행
- **세션 인계**: 컨텍스트가 길어지면 Claude 세션끼리 인계 메시지를 주고받으며 이어서 플레이한다
  (CLAUDE.md + LOG.md + 메모리가 인계 자료).

## 2.5 시작 과정: 빈 폴더에서 첫 비행까지 (약 2시간)
`docs/transcript-notes.md` §2에 분 단위 타임라인이 있다. 요약:
1. Steam 설치 경로를 찾고, 시작 질문 3개로 합의했다(난이도 Normal, kRPC + 자작 보조 모드, revert 정책).
2. GitHub에서 kRPC 0.6.0을 받아 설치했다. kRPC 서버가 자동으로 시작되지 않아서, 클릭 없이 켜려고 DLL 문자열과
   kRPC 소스를 뒤져 `autoStartServers` 설정 키를 찾았다.
3. **KSP를 디컴파일했다**(ilspycmd, .NET 버전이 안 맞아 `DOTNET_ROLL_FORWARD=Major` 우회). 여기서 .craft 파일
   형식, 연구와 시설 API, 에디터의 표면 부착 회전 규칙까지 읽어 냈다. 모드 작성부터 빌드 성공까지 약 12분 걸렸다.
4. KSP 안에서는 Unity `JsonUtility`가 기체 명세 JSON을 파싱하지 못해서, 작은 JSON 파서를 직접 넣었다.
5. 첫 연결에 성공해 커리어가 자동 생성됐다(자금 25,000). 시험 기체를 JSON으로 조립하고, 발사하고,
   낙하산으로 회수하는 과정이 20분 만에 동작했다.
6. 비행 코드 전체(상승부터 재진입까지)를 작성했다. 그리고 커리어에 손대기 전에 **샌드박스에서 무인으로 Minmus
   왕복 전 과정을 한 번 날려 검증했다**(약 41분). 이때 원궤도화가 과하게 되어 로켓이 다시 떨어지던 것을 수동
   분사로 살려 낸 일이 있었다. 방사형 부스터 4개가 최대 동압 근처에서 분리되며 코어 엔진을 부순 일도 있었는데,
   이것이 이후 "방사형 디커플러 없이 부스터를 코어에 직접 붙인다" 규칙의 기원이다.
7. 조사는 처음에 deepseek(codex)에 맡겼지만 사용량 한도로 실패했고, sonnet 서브에이전트가 웹 조사를 해서
   설계 가이드를 썼다. 그 사이 본 세션은 "어떤 LLM 세션이든 이것만 읽으면 이어서 플레이할 수 있게"를 목표로
   CLAUDE.md를 작성했다.
8. 화면 캡처는 처음에 Windows PowerShell로 데스크톱 전체를 찍었다. 나중에 kRPC의 게임 화면 캡처로 바꿨다.

## 3. 규칙 (사용자와 합의)
- Normal 난이도 커리어. 발사비, 연구비, 업그레이드 비용은 모두 정상적으로 지불한다.
- 오토파일럿 모드 금지. 비행 로직은 직접 작성한다.
- **Revert**: 처음에는 "기본적으로는 금지인데, 테스트시에나 (즉 발사 시도 자체 테스트가 아니라, 시스템 구축시)
  버그같은걸로 안될때는 허용"이었다가, 이후 "게임이 허용하는 revert라면 괜찮다"로 바뀌었다(발사 시점이나 VAB로
  되돌리기). revert할 수 있는 시점이 지나갔으면 손실은 그대로 확정한다. 퀵로드는 우리 도구가 실패를 일으켰을 때만
  쓴다. revert는 할 때마다 LOG.md에 이유와 함께 남긴다.
- **샌드박스 리허설 금지**(사용자, 2026-09-25): 처음에는 새 비행 코드를 샌드박스 세이브에서 먼저 시험했다. 그러다
  사용자가 샌드박스에서 너무 완벽하게 해 오는 게 아쉽다고 했고(7.5), 리허설 때문에 커리어가 너무 안전해졌다는
  이유로 규칙이 바뀌었다. 지금은 새 비행 코드가 커리어에서 처음 돈다. 샌드박스 세이브는 사진 찍을 때만 쓴다.
  커리어에서 `sandbox-orbit`(궤도 순간이동)은 거부된다.
- 실패해도 멈추지 않는다. 원인을 진단하고, 기록하고, 고친 다음 다시 난다. 사용자에게는 진짜 막혔을 때만 묻는다.
  "자율"은 질문하지 않는다는 뜻이지 생각 없이 움직인다는 뜻이 아니다. 큰 분사, 긴 대기, 재시도 앞에서는 7.9의
  체크포인트를 먼저 쓴다.
- 미션이 끝날 때마다 LOG.md에 일지를 남기고, `docs/record/career.json`에 발사 기록을 더하고, 새 기체 사진을 찍는다.

## 6. 우주선 설계의 진화
- JSON 명세로 설계한다(`crafts/*.json`). 부품, 부착 노드, 대칭, 스테이지를 지정하면 모드가 .craft를 만든다.
  발사대에 올리면 KSP가 계산한 스테이지별 Δv/TWR을 보고, 틀렸으면 회수(전액 환불)하고 다시 설계한다.
- SRB 클러스터를 쓸 때 방사형 디커플러를 빼고 측면 SRB를 코어 SRB에 직접 붙였다. 셋이 동시에 연소가
  끝나면 TD-12 하나로 한 번에 분리된다. 분리 충돌이 없다.
- 무거운 SRB 스택은 휜다 → 추력축이 0.3~0.4° 틀어져 포드 반응휠보다 5배 큰 토크가 생긴다 → `rigid` +
  `autostrut: Root`를 추가했다. 단, 측면 부스터에 autostrut를 걸면 스폰 순간 분해된다.
- 90 t급 SRB 로켓은 피치를 제어할 수단이 없다 → AV-R8 핀 4개 + 인라인 반응휠로 해결했다.
- 착륙선이 좁고 높으면 넘어진다 → FL-T200 코어 + 방사형 FL-T400 3개 + 다리 6개로 바꿨다(33°까지 기울어도 버팀).
- 현재 검증된 기체: `crafts/mun-lander-3.json` (43부품, 93 t, LKO 도달 후 착륙선 Δv 약 4100 m/s).

## 7. 어려웠던 점 (실패와 원인) — 글에서 제일 재미있을 부분
도구(코드) 버그:
- **상승 로직 버그**: 원지점이 65초 앞에 있는데도 -10° 피치로 최대 추력을 유지했다. 40 km에서 2.5 km/s가 돼
  과학 부품이 불탔다. → 원지점 도달 예상 시간이 35초 미만일 때만 2단계로 넘어가도록 고쳤다.
- **조립기 대칭 버그**: 대칭 복사본끼리 부착 반지름이 달랐다(1.285 vs 1.372 m).
- **착륙 제어 버그**: 속도 루프에 피드포워드가 없어서 감속 곡선보다 7 m/s 이상 늦었다 → 15 m/s로 접지해 넘어졌다.
  Minmus처럼 TWR이 28이나 되는 곳에서 더 심했다. 오프라인에서 재현한 뒤 고쳤다.
- **조우 판정 버그**: Mun 플라이바이 뒤에 오는 Minmus 조우를 채택해서 Mun 궤도로 가 버렸다.
- **Mun을 스친 Minmus 전이**: 전이 분사가 길어서 오차가 생겼고, 궤도가 Mun SOI 가장자리를 스쳤다(근접 거리
  1733 km). 그 정도면 영향이 작을 줄 알았는데, 플라이바이 뒤 원지점이 10만 km로 튀었다. 작은 보정 탐색으로는
  조우를 못 찾아서, 거친 격자 탐색 후 미세 조정하는 로직을 넣었다 → 52 m/s로 Minmus 조우 복구.
  같은 보정에서 도착 궤도 경사를 45° 이상으로 틀었다(측량 지점이 위도 35~37°에 있음).
- 흔들림(wobble)을 사람은 봤는데 기록기는 잡지 못했다 → 롤, 롤 속도, 받음각 진동 경보를 추가했다.

설계, 조종 실수 (Claude 자신의 실수):
- 뒤집혀 누운 착륙선으로 추력을 줘서 탈출하려다 지형에 부딪혔다(Bill 사망, revert). 교훈: 누운 착륙선은 그대로 두고 구조 계획을 세운다.
- 피치오버를 일부러 무게중심을 틀어서 만들려고 밸러스트를 달았다 → SRB가 타면서 토크가 커져 뒤집혔다(Jeb 사망, 확정).
- 포드 밑에 Science Jr를 달고 방열판을 뺐다 → 재진입 중 머리부터 떨어졌다(Bill 사망, 확정).

EVA 구현기 (진행 중):
- kRPC에는 EVA 기능이 없어서 모드에 EVA 호출(나가기/상태/깃발/탑승)을 넣었다. 탑승은 "해치 트리거 안에 있을 때만"이라는
  게임 규칙을 그대로 지킨다. 막 나온 커발은 해치에 매달려 있으므로(사용자가 기억해 낸 동작) 바로 탑승할 수 있다.
- 첫 시도에서는 "All hatches are obstructed"가 떴다. Mk1 포드의 네 방향(0/90/180/270°)을 드로그, 구, 온도계, 배터리가
  모두 막고 있었다. 이 사실은 포드 하나만 패드에 세워 놓고 커발이 나오는 위치를 측정해서 알아냈다(해치 = 90°).
- 패드와 궤도에서는 완벽했는데, **Minmus 표면에서는 커발이 나오자마자 1400 m/s로 튕겨 나갔다**(한 번은 착륙선도 산산조각
  났다. revert). autostrut를 의심해 빼 봤지만 같은 증상이었다. 패드에서 착륙 다리만 펼치고 해 보니 커발이 Ragdoll 상태가
  됐다 → 펼친 다리가 해치 쪽 커발을 치고, 중력이 약한 Minmus에서는 그 충돌이 크라켄급 속도로 증폭된다는 결론을 냈다.
  다리와 탱크 배치를 돌리는 중이다.

LLM 에이전트 운영 문제 (게임 밖에서 생긴 문제, 글감으로 제일 좋음):
- **세션 인계로 "멈추지 말고 계속하라"가 빠졌다.** 구축 세션이 비행 세션에 넘긴 인계 메시지가 체크리스트
  형식이었고, "실패해도 계속 플레이하라"는 문장이 없었다. 받은 세션은 Jeb이 죽자 멈추고 사용자에게 물었다.
  사용자가 다른 세션에서 "지침이 제대로 간거 맞아?"라고 묻자, 구축 세션이 원인을 스스로 진단했다:
  "메시지 자체에 '멈추지 말고 계속 플레이하라'는 지시가 빠져 있었다는 것이고, 이건 제 인계서 작성 실수입니다."
  그 뒤 CLAUDE.md 맨 위에 사용자의 원래 목표와 자율 진행 원칙("The job")을 적었다. 규칙을 바꿔도 이미 돌고
  있는 세션에는 자동으로 전달되지 않는다는 점도 드러났다(revert 규칙을 완화했을 때도 같은 일이 있었다).
- **권한 분류기가 revert를 막았고, 스스로 권한을 추가하려는 시도도 막았다.** revert는 "되돌릴 수 없는 로컬
  파괴"로, 설정 파일에 허용 규칙을 쓰는 것은 "자기 수정"으로 분류됐다. 사용자가 `!` 명령으로 직접 설정 파일을
  만들어야 했다(두 번 시도한 끝에 적용됨). 그 사이 Jeb의 사망이 확정됐다.
- **40분 동안 멈춰 있었다.** KSP가 꺼졌는데 명령에 타임아웃이 없어서 계속 기다렸고, 사용자가 보고 끄기
  전까지 아무도 몰랐다. 그 뒤로 모든 명령에 `timeout`을 건다.

게임, 환경 문제:
- revert를 연달아 하면 KSP 물리 상태가 꼬여서, 멀쩡한 기체가 패드에서 폭발했다 → 재시작하니 해결됐다.
- 기동 노드는 Mission Control 2만으로는 안 되고 Tracking Station 2도 필요했다(돈을 쓰고 나서 알았다).
- KSP 재시작 때문에 저장하지 않은 계약 수락이 날아갔다 → 재시작 전에 저장하도록 바꿨다.
- 비행을 시작할 때마다 KSP 확장팩 광고 팝업이 떠서 진행을 막았다 → 모드에 팝업 닫기 기능을 넣었다. 게임 소리는 자동으로 음소거한다.
- Claude Code의 권한 분류기가 revert 호출을 막은 적이 있다 → 그 사망은 그대로 확정했다.

사람이 개입한 지점: 자율 진행 원칙, revert 규칙 완화, 로켓 흔들림 지적, 음소거 요청, 기록과 관측을 우선하라는 원칙.

## 7.5 Bob 고립과 구조 (성공)

- **상황**: Mun 생물군계 탐사 중 Lowlands에서 Farside Crater로 "호핑"했는데, 옛 이륙 로직(거의 수직으로 올라가
  원점에서 원궤도화)이 ~850 m/s를 써 버려 Bob에게 891 m/s만 남았다. 지표 → Kerbin 귀환의 이론 최소치(~890)와
  같은 수준. 샌드박스로 테스트하러 나가면서 비행 장면을 떠나 revert 기회도 사라졌다. 계획 실수다.
- **재현 먼저**: 커리어에서 한 번 잘못 날면 끝이라, 샌드박스에서 같은 크레이터, 같은 질량(연료를 궤도에서 태워
  맞춤)으로 새 이륙 코드를 6번 시험했다. 두 번은 궤도를 지나쳐 Mun 탈출 궤도로 튀었고, 한 번은 피치가
  +72°/−30°로 요동쳤다. 최종판(지형 바로 위로 낮게 날며 가속, 탄도 정점이 목표 고도를 넘지 않게 상승 속도를
  제한)은 Bob과 같은 조건에서 ~695 m/s. 크레이터 벽을 넘느라 이론치(~570)보다 비싸다. 귀환 연소 실측 275 m/s.
- **판단**: 695 + 275 ≈ 970 > 891 → 직접 귀환 불가. Bob은 연료를 아끼며 착륙 상태로 대기.
- **구조 계획**: 지표 EVA는 금지(Minmus에서 EVA 순간 물리 폭주로 Jeb이 초속 400 m로 튕겨 나간 뒤 정한 규칙)라
  사람 옮겨 태우기 대신 연료 보급을 택했다. Klaw(집게) 연구(과학 250) → 무인 유조선이 Mun 궤도에서 Bob의
  착륙선을 붙잡아 연료를 넘겨주고 놓아준다. 이를 위해 랑데부/접근 코드를 새로 짠다(나중에 우주정거장
  도킹에도 그대로 쓰인다).
- 샌드박스 사고도 하나: 순간이동 직후 기체가 초당 875°로 돌며 착륙 엔진 연료를 다 태웠고, 추력이 0이 되자
  자동 분리 로직이 착륙선을 떼어내 포드만 Mun에 추락했다. 이후 "마지막 엔진은 절대 분리하지 않는다"를 넣었다.

- **샌드박스 금지 이후 첫 실전**: 사용자가 "샌드박스에서 너무 완벽하게 해 오는 게 아쉽다"고 해서, 구조 코드는
  리허설 없이 커리어에서 처음 돌렸다. 대신 커발 보호를 최우선으로 하고, 새 코드는 무인 유조선이 먼저 쓴다.
- **유조선 발사**: 첫 발사는 원궤도화 버그(다 탄 부스터를 달고 추력 0으로 연소 시간을 계산)로 revert.
  재발사해서 Mun 30 km 역행 궤도에 도착했다.
- **Bob 이륙**: 서쪽(270°)으로 이륙해서 궤도면을 유조선과 맞췄다. 목표 15 km였는데 35 km까지 올라가 ~750 m/s를 쓰고
  140 m/s가 남았다. 수평 속도가 붙으면 실효 중력이 줄어 탄도 정점이 계산보다 높아진다(고칠 목록에 올림).
- **랑데부 (커리어 첫 사용)**: 궤도면 맞추기 18 m/s → 궤도 20바퀴 위상 대기 → 요격 9 m/s + 보정 25 m/s →
  115 m에서 상대속도 제거 → 28 m 앞에 0.27 m/s로 정지. 이어서 Klaw를 펴고 0.3 m/s로 다가가 착륙선을 붙잡았다.
  부품 33개 모두 멀쩡했다. 연료 LF 292 / Ox 358을 Bob 탱크로 옮기고 놓아줬다.
- **마지막 함정**: 귀환 연소를 시작하자 착륙선이 초당 10~17°로 돌았다. 원인은 두 가지였다.
  ① 연료를 탱크 순서대로 채워 방사형 탱크 셋이 180 / 30 / 3으로 불균형 → 무게중심이 추력축에서 0.36 m 벗어났다.
  ② Bob은 과학자라 **SAS를 못 쓴다**(Mk1 포드엔 SAS 모듈 없음). 그래서 "SAS로 회전 멈추기" 코드가 헛돌며 무한 반복했다.
  연소를 끊고 오토파일럿(반작용휠 직접 제어)으로 회전을 멈춘 뒤, 탱크 채움 비율을 똑같이 맞추는 `balance-fuel`을
  만들었다. 그 뒤 255 m/s 귀환 연소는 흔들림 없이 끝났고, 근지점 33 km로 재진입해 Kerbin 바다에 착수했다. **Bob 귀환.**
- 이득 계산: Normal 난이도에선 죽은 커발도 나중에 돌아오니 게임 수치상 이득은 크지 않다(경험치·평판·회수 정도).
  진짜 수확은 랑데부 → 붙잡기 → 연료 이송이 실전에서 검증된 것. 연료 보급 정거장과 도킹의 기반이다.

## 7.6 Minmus 과학 투어와 "저고도 조사" 계약 (Minmus Science 1)

- **동기**: Bob 구조 뒤 과학이 30점뿐이라 중계위성 연구도 못 했다. 이미 연구해 둔 기압계와 SC-9001 Science Jr.(재료 실험실)를
  착륙선에 한 번도 안 실었다는 걸 깨닫고, ML7 설계에 Science Jr. 2개, goo, 기압계, **Experiment Storage Unit**(저장 상자)을 붙였다.
  착륙지마다 실험을 돌리고 데이터를 포드 옆 상자에 모아 오면, 전송(일부만 인정)이 아니라 회수로 전액을 받는다.
- **실수 1**: 궤도에서 Science Jr. 두 개가 동시에 돌았다. 같은 실험 두 번째 사본은 가치가 거의 없다. → 한 번에 주제당 실험 하나만.
- **"Collect All"의 함정**: 저장 상자의 버튼(이벤트)은 비행 중 비활성인데, 액션 그룹용 액션은 동작한다. 덤으로, 데이터를 옮기면
  Science Jr.를 다시 쓸 수 있어서 재료 실험을 네 곳에서 했다.
- **저고도 조사 계약**: "Minmus 상공 5,100 m 아래, 웨이포인트 근처에서 승무원 보고". 14 km 궤도 통과는 인정되지 않았다.
  사용자가 "노하우를 조사해 보라"고 해서 KSP 코드를 디컴파일해 판정식을 찾았다: 고도는 해수면 기준, 수평 반경은
  (500 + 15000) / 2 = **7.75 km**. grok 웹 검색으로도 교차 확인했다. 방법: 통과 반 바퀴 전에 근지점을 웨이포인트 위
  (상한 − 1 km)로 낮추고(약 5 m/s), 1/4바퀴 전에 궤도면을 틀어(10~18 m/s) 웨이포인트 바로 위를 지나게 한다.
  낮은 호 전체가 지형보다 800 m 이상 높을 때만 실행한다. 결과: 43 m, 188 m, 735 m 거리로 통과, 계약 완료(+166k).
  kRPC는 완료된 파라미터를 계속 "미완료"로 보여 줘서, 웨이포인트가 지도에서 사라지는지로 판정해야 했다.
- **실수 2 (퀵로드)**: 이륙 오버슈트를 고친다고 넣은 규칙이 Minmus(TWR 18)에서 역효과를 내, 1초 사이에 궤도속도를 지나쳐
  Minmus 탈출 궤도(667 m/s)로 튀었다. 우리 툴링 버그라 규칙대로 퀵로드. 가속도 상한(3 g 또는 30초에 궤도속도)과
  "원지점이 목표의 1.5배를 넘으면 즉시 중단"을 넣은 뒤로는 이륙마다 약 230 m/s.
- **성과**: Lowlands, Greater Flats, Midlands, Great Flats 착륙. 회수 후 과학 **105 → 670**, 자금 1.31M.
  그 과학으로 중계 안테나(precisionEngineering)와 **Nerv 핵엔진**(nuclearPropulsion)을 연구했다.

## 7.7 구조와 회수: 계약은 사라지고, 클로는 튕겨 나가고
듀나 창까지 두 달 반이 남아 궤도 계약을 몇 개 했다. 결과는 반쯤 실패다.
- **빈 구조선**: 무인 구조선 Rescue 1로 케르빈 궤도의 Beafrod을 구하러 갔다. 클로로 캐빈을 잡았는데 안이 비어
  있었다. kRPC의 발사 함수는 저장 없이 곧바로 비행 장면으로 넘어간다. 그래서 우주센터에서 수락한 계약이 비행
  장면에서 "제안" 상태로 되돌아갔고, 구조 대상 커발도 함께 사라졌다. 선금만 남았다. 이제 수락과 발사 직전에
  저장한다. 결합할 때 12 m짜리 긴 기체가 8.6 m 거리에서 방향을 틀다가 앞코로 캐빈을 치기도 했다
  (`docs/media/2026-09-25_rescue-1_approach.png`).
- **CommNet 신호 필수**(사용자 결정): 무인 탐사선은 KSC와 신호가 이어져야 조종된다. OKTO 내장 안테나는
  트래킹 스테이션 2레벨 기준으로 약 15.8 Mm까지만 닿는다. 민머스(47 Mm)에서는 조종이 안 된다는 뜻이다.
- **첫 중계위성**: 계약이 지정한 극궤도(경사 90°, LAN 205°, 1,259×1,883 km)에 RA-2 중계기를 올렸다.
  발사대의 관성 경도가 목표 LAN에 올 때까지 기다렸다가 북쪽으로 발사했다. 새 `match-orbit`이 궤도면, 근점,
  원점을 차례로 맞췄다(`docs/media/2026-09-25_polar-relay-1.png`).
- **Thud를 끝내 못 잡다**: 민머스 궤도에 떠 있는 Mk-55 "Thud" 엔진 하나를 회수하는 계약이었다(25.6만).
  두 번 갔다. 한 번은 엔진만으로, 한 번은 RCS를 새로 연구해 달고 갔다. 디컴파일해 보니 클로는 중심에서
  0.1 m짜리 광선 하나를 쏘고, 그 광선이 표면에 43° 안으로 맞아야 잡는다. kRPC 광선으로 Thud 표면을 재서
  가장 평평한 면도 찾았다. RCS로 그 면에 수직으로, 축 오차 3~9 cm, 0.15 m/s로 들어갔다. 그래도 닿을 때마다
  0.5 m/s로 튕겨 나왔고 Thud는 빙글빙글 돌았다. 회전은 잠깐 시간가속을 걸면 멈춘다는 스톡 규칙으로 해결했다.
  하지만 끝내 잡지 못했다. 사용자와 합의해 멈췄고, 작은 부품 회수 계약은 앞으로 받지 않는다.
- 버그도 여럿 드러났다. 궤도면을 90° 바꾸는 튜너가 궤도 에너지를 보지 않아 민머스 탈출 궤도로 가 버렸다.
  복구 분사는 쌍곡선 궤도에서 틀린 속도값을 받아 반대로 밀었다. 원궤도 보정은 2분간 전력 분사해서
  탈출 궤도를 만들었다(발사 시점으로 되돌림). 모두 고쳤다.

## 7.8 Duna 1: 첫 행성 착륙, 그리고 600일 대기
처음으로 다른 행성에 간 유인 비행이다. 조종사는 Valentina. 한 번은 도착하고 나서 되돌렸고, 두 번째에
착륙했다. 착륙도 계획대로 되지는 않았다.

![Duna 1 발사대](media/2026-09-25_duna-1_pad.png)
*Duna 1. 맨 위가 착륙선(포드 + 방사형 탱크 3개 + Terrier), 그 아래가 Poodle 전이 단이다.*

- **기체**: 커리어 VAB에서 조립했다(42부품, 84.8 t, 42.9k). 저궤도 79×80 km에 올라가니 Poodle 단 1197 m/s,
  착륙선 3893 m/s가 남았다. 샌드박스 리허설 때와 같은 값이다.
- **첫 시도: 도착 속도 1364 m/s**: 탈출 분사 1072 m/s와 보정 2.7 m/s로 Duna 근지점 60 km를 맞췄다. 그런데 도착
  궤도 경사가 124°, 즉 역행이었다. 태양 궤도에서 `correct --inc-to 10`을 돌렸더니 0.1 m/s짜리 국소 최적(경사 50°)에
  걸려 멈췄다. 그 거리에서는 0.1 m/s가 Duna 통과 지점을 약 3,500 km나 옮긴다. 그러니 0.5 m/s 간격으로 짠 초기
  격자가 목표를 통째로 건너뛴 것이다. 0.05 m/s 격자를 더해서 0.4 m/s로 경사 9.7°를 만들었다. 도착 48일 전부터
  근지점을 계속 다듬었는데, 이건 잡음을 쫓는 일이었다. 기체 방향을 바꾸기만 해도 몇 mm/s가 생기고, 그게 통과
  지점을 수백 km 옮긴다(사용자가 목표 지점이 왜 자꾸 움직이냐고 물었다). 미세 보정은 SOI 안에 들어가서 한다.
  진짜 문제는 Duna SOI에 들어가서야 보였다. **도착 v_inf가 1364 m/s**였다(샌드박스에서는 약 760). 60 km 원궤도로
  포획하는 데만 966 m/s가 들고, 착륙과 귀환에 쓸 몫은 약 −50 m/s가 된다. 원인은 도구였다. `transfer_planet`이
  탈출 분사 크기를 Duna 궤도의 장반경(20.7 Gm)에 맞췄는데, 도착할 때 Duna는 근일점 근처(19.7~20.2 Gm)에 있었다.
  남는 에너지를 근지점만 보는 튜너가 분사 방향을 비틀어 맞추다 보니, 경로가 Duna 궤도를 일찍 가로질렀다.
  295일이 걸려야 할 비행이 194일이 됐고, 태양 근일점은 13.33 Gm으로 Kerbin 궤도보다 안쪽이었다. 탈출 분사 때
  노드가 예측한 조우에 이미 도착 경사 123.6°가 찍혀 있었는데, 그냥 워프로 넘어갔다. 그 190일 동안 아무도 몰랐다.
  게임이 revert를 허용했고, 도구 버그였고, 승무원 안전 문제라 **발사 시점으로 revert**했다. 수정: 탈출 분사를 도착
  시점 목표의 반지름 기준으로 계산하고, 튜너 비용에 도착 v_inf / 10을 더하고, v_inf가 호만 값의 1.25배 + 50을
  넘으면 분사를 거부한다.
- **재발사**(같은 UT): 탈출 분사 1055 m/s(계획 v_inf 868), 튜닝 후 예상 도착 v_inf 1037, 보정 3.6 m/s, 경사
  9.3° 순행. Duna SOI에 들어가서 v_inf 1067을 확인했고, SOI 안에서 `correct --inc-to 10` 6.3 m/s로 근지점 59.5 km를
  맞췄다.
- **타원 포획**: 59×1007 km 궤도로 잡았다(539 m/s. 도중에 Poodle 연료가 떨어져 분리됐고 Terrier가 마무리했다).
  60 km 원궤도 대신 긴 타원으로 잡으면 약 220 m/s를 아낀다. 착륙에는 손해가 없다. 원지점에서
  `periapsis --alt 5000`으로 근지점만 내리면 되고, 그건 19 m/s다. 궤도 과학 161(승무원 보고 35, goo 70, 온도계
  56)에 궤도 EVA 보고 56("Duna Lowlands 바로 위 우주")까지 모아 기체에 실어 뒀다.
- **착륙: 스크립트가 28 km에서 죽다**: `land`가 고도 28 km, 속도 1120 m/s 지점에서 예외를 던지고 죽었다(한때
  초당 33°로 텀블링했다). kRPC의 `Parachute.deployed`가 착륙선의 Mk2-R 낙하산 3개에서 NullReferenceException을
  냈다. 이 낙하산들은 Terrier와 같은 스테이지에 묶여 있어서, 포획 때 진공에서 이미 활성화됐다. 그 바람에
  "Safe to deploy?" 필드가 사라진 상태였다. 사람이 탄 기체가 Duna 대기로 떨어지는 중이었다. 낙하산 호출을
  예외로 감싸고 같은 `_powered_descent`를 부르는 비상 스크립트를 그 자리에서 써서, 지표 12 km, 925 m/s에서
  동력 하강을 시작했다. **15.71°N 156.21°E Midlands에 1.4 m/s, 기울기 9.4°로 착륙**했다. Mk2-R은 끝내 펴지지
  않았고, 엔진만으로 내렸다. 착륙에 쓴 Δv는 질량 기준 약 656 m/s. 이후 `_chute_deployed()`가 이 오류를 견디게
  고쳤고(land, liftoff), 설계 교훈을 하나 남겼다. 착륙선 낙하산은 엔진과 같은 스테이지에 두지 말고 자기
  스테이지를 준다.
- **600일 기다리기**: 지표 과학 161(승무원 보고 35, goo 70, 온도계 56)도 실어 뒀다. 남은 연료는 LF 376.8 /
  Ox 460.6, 7.43 t, 진공 기준 **약 2800 m/s**. 이륙 약 1450과 탈출 약 740에 충분하다. 문제는 창이다. Duna→Kerbin
  귀환 창은 **UT 22,895,340, 600.8일 뒤**(비행 297일)에 열린다. Valentina는 Midlands에 착륙한 채 그때까지 기다리고,
  그동안 다른 임무를 한다.

*비상 스크립트의 동력 하강. 낙하산은 한 번도 펴지지 않았다.*

## 7.9 판단 과정 점검: "명령이 끝났다"는 "잘됐다"가 아니다
Duna 1부터 구조 임무까지 몇 시간 동안 사용자가 여러 번 끼어들어야 했다. 궤도를 거꾸로 뒤집은 분사, 17분짜리 대기, 계속
튕겨 나가는 Klaw. 사용자는 상황마다 땜질할 게 아니라 판단 과정 자체를 바꿔야 한다고 했다.

- **무슨 일이 있었나**:
  - 계약용 동기궤도 중계위성 Keo Relay 2에서 `match-orbit`의 원지점 분사(1602 m/s)가 **궤도를 역행으로 뒤집었다**
    (경사 158°, 같은 궤도면을 거꾸로 도는 궤도). 목표는 거의 원형(e 0.007)이라 계약이 근점 인수(argPe)를 보지도
    않는데, 비용 함수가 argPe 오차에 가중치를 줬고 경사 항은 아예 없었다. 같은 분사가 Relay 1에서는 523 m/s였고,
    1602라는 숫자는 78분 전에 이미 화면에 찍혀 있었다. 발사 후 몇 시간이 지나 revert도 못 했다. 원지점을
    9,000 km까지 올린 뒤 거기서 속도를 뒤집는 쌍타원 반전으로 복구했다.
  - 구조선의 궤도가 Klaw를 붙이려고 움직이는 사이 64.8×80.7 km까지 가라앉았다. 어차피 임무를 끝낼 수 없는
    기체였는데, 근지점을 올리려고 **실시간 17분짜리 대기**를 반사적으로 시작했다(대기권 안이라 워프가 안 된다).
    답은 revert였다. 사용자는 이 판단들의 근거와 순서가 뭐냐고 물었다.
  - Rescue 2는 엔진만 달린 Rescue 1 설계를 그대로 다시 썼고, **튕겨 나가는 grab을 같은 방식으로 몇 번이나
    반복했다**. 사용자가 revert하고 RCS를 쓰라고 했고, 그다음에는 지금 revert하라고 했다.
  - 그 밖에: 태양 궤도에서 잡음 수준의 보정 쫓기, 다 탄 SRB를 70 km까지 달고 올라간 일(사용자가 화면에서 발견),
    유인 Duna 진입 중 착륙 스크립트 사망.
- **점검 방식**: 사용자는 긴 컨텍스트 탓에 이전 세션의 판단력이 떨어졌다고 보고, 그 세션이 CLAUDE.md를 직접
  고치지 못하게 했다. 새 세션이 사건 목록, LOG.md, 최근 커밋 diff를 읽고, 같은 자료를 별도 모델(fable-5)에 넘겨
  독립 진단을 받은 뒤 사용자에게 한국어로 보고했다.
- **진단**: 사건 하나하나가 아니라 패턴이 문제였다.
  1. 명령이 스스로 출력한 "완료"를 임무 성공으로 읽었다. Duna 탈출 분사는 도착 경사 123.6°를 출력했는데 그냥
     워프로 넘겼고, Keo Relay 2의 1602 m/s도 78분 앞서 보였다.
  2. 단계를 시작하기 전에 기대 수치를 말하지 않았다. 기준이 없으니 이상한 숫자가 이상해 보일 수가 없었다.
  3. 계획기(planner)가 자기가 튜닝한 노드를 검사 없이 그대로 태웠다. 가장 비싼 오류 두 개는 코드가 결정했다.
  4. 가설도 횟수 제한도 없이 재시도했다.
  5. 비행 단계가 도는 동안 코드와 문서 같은 곁일을 했다.
  6. 메모리 14개 중 9개가 사건 하나에서 나온 규칙이었다. "상태를 확인하라", "선택지를 따져라"를 말하는 세 개는
     지켜지지 않았다.
  긴 컨텍스트가 주원인은 아니었다. Duna 오류는 새 세션을 시작한 지 13분 만에 났다.
- **적용한 것**(사용자가 전부 동의): CLAUDE.md에 **"How to decide" 필수 체크포인트**를 넣었다. 100 m/s가 넘거나
  스테이지 Δv의 20 %를 넘는 분사, 실제 시간 5분이 넘는 대기, 방금 실패한 것의 재시도, 예상과 다른 숫자, 복구나
  수정 명령 앞에서는 반드시 한국어 진행 메모 하나에 네 줄을 쓰고 나서 움직인다.
  1. **기대**: 이 단계가 낼 숫자(Δv, 근지점/원지점/경사, 도착 v_inf, 시간)와 그 출처
  2. **비용**: 남은 Δv 대 필요한 Δv, 그리고 실제 시간(레일 워프는 진공에서 추력이 없을 때만 된다)
  3. **선택지**: 최소 두 개. "revert/회수"와 "멈추고 진단"은 늘 포함한다. 이 기체가 아직 제 일을 할 수 있나?
     못 하는데 게임이 revert를 허용하면 지금 revert한다.
  4. **중단 규칙**: 이 선택지를 버릴 관측값(숫자로, 최대 3회)

  단계가 끝나면 명령의 "done"이 아니라 1번 줄과 결과를 비교한다. 메모리 세 개(revert-early,
  weigh-options-before-acting, observe-before-fixing)는 이 체크포인트 안으로 합쳤다.
- **코드 게이트**: 모든 계획기의 튜닝된 노드는 `_approve`를 통과해야 한다. Δv가 해석적 추정치의 1.5배 + 20을
  넘거나, 궤도가 뒤집히거나, 근지점이 대기 속으로 들어가면 거부하고 노드만 남긴다. `transfer`, `correct`,
  `match-orbit`, `return`에 `--plan`을 붙이면 노드에서 멈추고, 예측 궤도를 읽은 뒤 `ksp node`로 태운다. 태양
  궤도에서는 1 m/s 미만 보정을 하지 않는다. `grab`은 접촉 3회에서 멈춘다(`--max-contacts 3`). land, land_atmo,
  reentry는 하강 중 예외가 나면 낙하산 + 동력 하강으로 넘어간다. 대기권 안에서 기다릴 때는 실제 시간이 얼마나
  드는지 말한다. 모의 궤도로 오프라인 시험을 했고, Keo Relay 2를 뒤집은 노드는 거부됐다.
- **그런데 바로 다음 비행에서 놓쳤다**: 점검 직후 Rescue 3를 다시 날렸다. `intercept`가 96바퀴 위상 대기
  (185,664초. 90 km에서 레일 워프는 50배라 실제로 약 1시간)를 예고했는데, 그냥 기다렸다. 체크포인트 메모에는
  "진공, 워프 가능"이라고만 쓰고 대기 시간은 계산하지 않았다. 이번에도 사용자가 잡았다. 네 줄을 적는 것과
  그 숫자를 실제로 계산하는 것은 다른 일이다. 대기를 멈추고 `phase_orbit`(아래 7.10)을 새로 만들었고, LOG.md의
  다음 할 일 맨 위에 "위상 대기를 포함해 실제 시간까지 기대 수치를 말한다"를 올렸다.

## 7.10 Klaw 미스터리 풀림: 버그는 우리 쪽에 있었다
7.7에서 끝내 못 잡은 Thud, 그리고 Gwenbro 구조까지. 몇 시간 동안 Klaw는 닿기만 하면 튕겨 나왔다. 원인은 기하도
속도도 아니고, 우리 기체 조립기였다.

- **증상**: Salvage 1/2(Minmus의 Thud)와 Rescue 2/3(Kerbin 궤도의 Mk1 Lander Can, Gwenbro)에서 정면으로 천천히
  닿는 접촉은 한 번도 잡히지 않았다. 유일하게 잡힌 건 Rescue 1이 흔들리다 축에서 벗어나 앞코로 들이받은 한
  번뿐이다. 그래서 광선 각도, 평평한 면, 접근 속도, RCS 같은 기하 쪽을 계속 팠다.
- **조건은 전부 참이었다**: Rescue 3 첫 비행에서 `GrappleDebug`로 접촉 순간을 찍었다. Klaw 노드의 광선이
  Lander Can에 **0.010 m, dot 1.000**으로 몇 초 동안 맞고 있었다(잡는 조건은 0.1 m 미만, 0.733 초과). 그런데
  상태 머신(FSM)은 계속 "Ready"였다. 디컴파일한 `on_contact`의 나머지 조건까지 평가하도록 디버그를 늘리고 KSP를
  재시작해서 다시 날았다. 광선 0.010 m, dot 1.000, 어저스터 0, 상대속도 0.39~0.50 m/s(< 1), `OnCheckCondition` 참.
  **조건이 전부 참인데도** FSM은 Ready에 머물렀다.
- **KSP.log에 답이 있었다**: 매 FixedUpdate마다 "[Grapple Module] Grabbing on to Mk1 Lander Can"이 찍히고,
  바로 뒤에 `NullReferenceException at ModuleGrappleNode.Grapple`이 따라 나왔다. 잡으려는 순간마다 예외로 죽었고,
  그게 밖에서는 "튕김"으로 보였던 것이다.
- **원인**: 디컴파일해 보니 `grappleNode`(AttachNode)는 비행 장면의 `OnLoad`에서만 만들어진다. 그런데 우리
  CraftBuilder는 .craft 파일에 MODULE 노드를 하나도 쓰지 않았다(Rescue 3.craft에 0개). 그래서 발사할 때 KSP가
  모듈의 OnLoad를 부르지 않았고, grappleNode는 null로 남았고, 잡을 때마다 NRE가 났다. Salvage 1/2와 Rescue 2/3이
  전부 이걸로 설명된다. Rescue 1이 한 번 잡은 것은 KSP 재시작 뒤였다. 기체를 세이브에서 다시 읽었고, 세이브에는
  MODULE 노드가 있다. 교훈: 스톡 메커니즘이 "안 먹힐" 때는 KSP.log부터 읽는다. 누군가 로그를 들여다보기 전에
  몇 시간이 기하와 속도에 들어갔다.
- **시험과 구조**: 우주센터로 나갔다가 `fly`로 기체를 다시 불러오니 **첫 접촉에 잡혔다. 튕김 0회, NRE 없음.**
  이어서 `transfer-crew`가 예외를 던졌다(kRPC `TransferCrew`는 `crew.seat.part`를 쓰는데, 결합 뒤 Gwenbro에게는
  좌석 객체가 없었다). 한 번 더 재로드하니 해결됐다. "Save Gwenbro" 계약은 이미 세이브에서 Complete였다(우리
  `contracts` 명령은 kRPC의 parameter.completed = false를 그대로 보여 준다. 표시 버그다). 캔을 놓아주고
  `periapsis --alt 30000`(48 m/s)으로 30.2×89 km, `reentry --keep-until 300`: 드로그 20 km, 주 낙하산 4 km에서
  227 m/s, 서비스 모듈은 301 m에서 분리, 착수, 회수. **Rescue Gwenbro 완료**, 자금 2.52M, 평판 340.
- **근본 수정**: 사용자는 재로드 우회가 아니라 근본 수정을 원했다. CraftBuilder가 이제 VAB처럼 프리팹에서 부품
  모듈마다 MODULE 노드를 하나씩 저장한다(Rescue 3.craft에 208개). 발사대 시험에서 스테이지별 Δv/TWR은 그대로였고,
  새로 발사한 기체에서도 `grappleNode = True`가 나왔다. 승무원 이동은 KspBot `MoveCrew`로 새로 만들었다. 좌석이
  아니라 부품의 승무원 목록으로 옮기고 onCrewTransferred를 발생시킨다(`transfer-crew --to mk1pod.v2`, 비행에서는
  아직 미검증).
- **같은 비행의 또 다른 버그: kRPC `orbital_speed_at`**: 96바퀴 대기를 멈춘 뒤 새로 짠 `phase_orbit`은 원지점을
  N바퀴 동안 올렸다가 다시 원궤도로 내려서, 목표가 출발점에 오도록 맞춘다(계획 6바퀴, 원지점 176 km, 66 m/s × 2).
  그런데 **되돌리는 분사가 −66 m/s가 아니라 +172 m/s로 나갔다.** kRPC `Orbit.orbital_speed_at(UT)`는 미래 시각을
  주면 다른 지점의 속도를 돌려준다(+600초를 물으면 +0초나 +1200초의 값이 나왔다). 궤도가 89×482 km로 찌그러졌고,
  요격 129 m/s에 "보정" 342 m/s가 붙었다. 계획은 약 140 m/s였는데 709 m/s를 썼다(남은 2441 m/s, 임무에는 충분).
  수정: radius_at으로 계산하는 vis-viva `flight.speed_at`(검증함)으로 모든 `orbital_speed_at`을 바꿨다. match_orbit
  분사 1/2와 궤도면 변경 교차점도 포함이다. Keo Relay 2의 1602 m/s도 일부는 이 탓이었을 가능성이 크다. 7.7에서
  쌍곡선 궤도의 복구 분사가 거꾸로 민 것도 같은 함수였다. 랑데부 요격/보정 분사도 이제 `_approve`를 거친다
  (이번의 129 m/s(예상 약 6)와 342 m/s는 거부됐을 것이다). `phase_orbit`은 되돌린 궤도가 찌그러져 있으면 더 진행하지
  않는다. 결합 전 대기 거리는 51.7 m.
- **실전 검증: Rescue 4(Minmus 궤도의 Mitbro)**: 고친 조립기로 만든 첫 기체다. Rescue 3에 Communotron 16-S를
  더했다(OKTO 내장 안테나는 Minmus까지 닿지 않는다). 전이 분사는 930 m/s(예상 921)였는데, 분사 도중 Swivel 단이
  분리되면서 조우가 어긋나 27 m/s로 바로 되살렸다. 포획 218 m/s(예상 216), 궤도면 57.3° 맞추기 90.7 m/s, 요격과 보정
  33 m/s. 그리고 **발사 직후 기체가 재로드 없이 첫 접촉에 잡았다. NRE도 없었다.** 처음 써 본 `transfer-crew`(MoveCrew)가
  Mitbro를 포드로 옮겼고, 세이브의 계약 조건도 Complete로 바뀌었다. 귀환 때는 게이트가 `return --plan`의 224 m/s를
  "예상 40"과 비교해 거부했다. 이번엔 분사가 아니라 추정식이 틀렸다(Kerbin 근지점을 낮추는 데 드는 v_inf를 빠뜨렸다).
  식을 고치고 태웠다. 밤의 초원에 착륙, **Mitbro 구조 완료**, 자금 2.84M, 평판 368.

## 7.11 Eve 1: 첫 행성간 브로큰-플레인 전이
구조 임무를 끝내고 보니 과학이 45점뿐이었다. 다음 기술 노드는 160~550점이다. opus 서브에이전트가 세이브를
파싱해 과학 현황을 조사했다. 고궤도 과학은 어느 천체에서도 딴 적이 없었다. 궤도 EVA 보고는 바이옴마다 따로
인정된다. 자금을 과학으로 바꾸는 전략은 10k당 1점 수준이라 쓸모가 없었다. 그리고 Minmus 표면 재료 실험이
9개 바이옴 모두 0/125였다(7.6에서 딴 줄 알았던 약 500점의 정체는 7.12에서 풀린다). 그래서 아직 아무도 안 간
Eve로 과학을 따러 가기로 했다. 조종사는 Jeb.

- **기체**: Duna 1에서 다리와 착륙선 낙하산을 빼고, goo와 온도계를 한 세트 더, 기압계 2개(고우주·저우주용)를
  붙였다. 스택 전체에 스트럿을 걸었다(84.6 t, 40부품, 44.5k). 상승 중 회전 속도는 최대 1.6°/s, 최대 동압 33 kPa로
  조용했다. 저궤도 79.4×79.7 km에서 Poodle 1251 + Terrier 4105 m/s.
- **첫 시도: 계획기가 Eve에 닿지 못하다**: `transfer Eve --plan`이 조우를 찾지 못했다. 최근접 거리를 줄이려던
  튜너가 탈출 분사를 1172 m/s까지 부풀렸다(v_inf 943, 호만 약 780). 태양 근일점이 9.14 Gm으로 Eve 궤도(9.83)보다
  안쪽이었고, 방사 방향 성분 때문에 탈출 근지점이 67 km, 즉 대기 속이었다. 7.9에서 넣은 `_approve` 게이트가 이
  노드를 **거부했다. 게이트가 실전에서 잡아낸 첫 사례다.** 원인은 Eve의 궤도 경사 2.1°였다. 궤도면 안에서만
  시작점을 잡는 탐색으로는 궤도면 밖으로 나가는 경로를 찾을 수 없다. 경사가 0.06°인 Duna에서는 드러나지 않았다.
  같은 비행에서 저궤도 `eva out`도 "hatch obstructed"로 막혔다. 기압계를 90° 위치, 즉 Mk1 포드 해치 자리에
  달았던 것이다. 설계 가이드에 이미 적혀 있었는데 확인하지 않았다. EVA 과학도 못 하고 계획기도 고쳐야 해서
  **발사 시점으로 revert**했다. 계기를 225/270/315°로 옮기고, 발사대에서 EVA 나가기와 탑승을 확인했다.
- **계획기 재설계(fable)**: 적도 저궤도에서는 Eve의 궤도면을 탈출 분사 하나로 맞출 수 없다. 창이 열릴 때 Eve는
  우리 궤도면에서 347 Mm 떨어진 곳에 도착한다(Eve SOI는 85 Mm). 한 번의 분사로 가는 3차원 Lambert 해는 탈출
  점근선의 적위가 48~66°여야 하고, 그러려면 약 2180 m/s가 든다. 그래서 **브로큰-플레인 전이**를 넣었다. 목표의

  튜닝한다(방사 성분을 빼면 탈출 근지점이 분사 고도에 그대로 남는다). 목표가 우리 궤도면에서 SOI보다 멀면
  중간 보정 시각과 예상 Δv를 출력한다. 천체 데이터만으로 오프라인 검증을 했다. Eve 창은 비행 184일, v_inf 790,

  탈출 약 1040, Eve는 궤도면 밖 −347 Mm, 궤도면 변경 약 413"을 출력했다. 오프라인 숫자와 똑같았다. 튜닝된 노드는

## 7.12 Minmus Science 2: 사라진 재료 과학의 정체
7.11의 조사에서 이상한 게 하나 나왔다. Minmus Science 1(7.6)은 바이옴마다 "materials 100"을 출력했는데, 세이브의
Minmus 표면 재료 실험은 9개 바이옴 모두 0이었다. Eve 1 준비 때의 가설은 저장 상자의 Collect All이 재실행할 수
없는 Science Jr 데이터를 가져가다 날렸다는 것이었다. 이 가설은 틀렸다.

  ModuleScienceExperiment를 디컴파일해 보니 Collect All은 goo와 재료 실험을 똑같이 처리한다. 실제로 같은 비행의 goo는
  인정됐다. 그러니 메커니즘은 문제가 아니었다. MS1이 바이옴마다 찍은 "materials 100"은 궤도에서 돌린 사본(저궤도

## 7.13 Survey 1: 착륙 없이 1600점
세이브를 다시 보니 우주 과목이 거의 비어 있었다. Mun과 Minmus의 바이옴별 궤도 EVA 보고, 자력계(기본 45 × 천체
배수), 천체마다의 고우주 세트. 유인 궤도선 하나면 착륙 없이 전부 딸 수 있다. 조종사는 다시 Bob.

- **기체**: Eve 1 스택에서 포드 측면 부품을 225/270/315/0°에만 뒀다(해치 자리는 비움, 저장 상자는 315°). Science
  Jr 3개, 자력계 붐은 Terrier 탱크에 달았다. 발사대 EVA 시험에서 나가는 건 됐는데, Bob이 포드에서 둥실 떠올랐다가
  발사대로 떨어졌다(Ragdoll 상태, 생존). 다시 태우려고 **발사 시점으로 revert**했다. 저궤도에서 Poodle 약 1050 +
  Terrier 3623 m/s.
- **조준점 시드 v2**: Mun 전이 865 m/s(예상 857). 분사 뒤 Mun 근지점이 −5.6 km, 도착 궤도는 역행 적도였다. 7.11의
  조준점 시드(직선으로 b/t 근사)를 Kerbin 궤도에서 쓰니 경사 167°밖에 안 나왔다. SOI 밖에서는 분사가 조준점을
  Δv × t만큼 옮기지 않기 때문이다. v2는 KSP가 직접 예측한 충돌 벡터의 수치 야코비안(시험 노드 3개, 한 번 재선형화)으로
  최소 노름 분사를 구하고, 36개 조준 각도를 실제 궤도 패치로 판정한다. 결과는 116 m/s로 경사 98°. 전이 직후
  노드선 근처의 법선 분사는 지렛대가 작아서 비쌌지만, 예산(약 3800 대 필요 약 1200)이 넉넉해 받아들였다. Kerbin
  고우주에서 자력계 67.5를 포함해 7개 과목 전부, Mun 고우주와 저우주 세트를 땄다. 포획 279 m/s(예상 279), 14×17 km.
- **자력계는 7초 걸린다**: `do_science`는 1.5초 뒤에 데이터를 모았는데, 자력계는 보고까지 약 7초가 걸린다. 다음
  호출이 반쯤 진행된 실험을 "쓸모없는 데이터"로 보고 리셋해서, Mun 저궤도 자력계 값을 한 번 잃었다. 이제는 시작한
  실험이 모두 데이터를 낼 때까지 최대 20초 기다린다. 다시 돌려 135점.
- **지상 궤적으로 바이옴 순회**: 새 스크립트는 지상 궤적을 예측해 아직 안 딴 바이옴에 다음으로 들어가는 시각을
  찾고, 그 통과의 한가운데로 워프해서 EVA, 보고, 탑승을 한다. **Mun 바이옴 17개 전부**의 저궤도 EVA 보고를 땄다.
- **말없이 막힌 탑승**: 출력되는 보고 제목이 실제 과목보다 한 박자 늦었다. 세이브를 보니 PolarLowlands와
  NorthwestCrater가 다른 제목으로 저장돼 있었다. 그러다 중복 보고 하나 때문에 포드가 커발의 데이터를 거부했고,
  KSP가 "Cannot store experiments / Board anyway" 팝업(KerbalEVA.checkExperiments)을 띄웠다. `eva board`는 에러 없이
  아무것도 하지 않았다. 중복을 버리고 탑승한 뒤 팝업을 닫았다.
- **Mun에서 Minmus로: 극궤도가 길을 막다**: `transfer Minmus`를 Mun 궤도에서 부르면 `transfer_planet`으로 가도록
  달 사이 전이로 일반화했다. 문제가 셋 나왔다. (1) 창을 찾을 때 40일을 거슬러 보는데, Mun→Minmus 창은 7.4일마다
  오니 다섯 주기 전 창을 골랐다. 거슬러 보는 범위를 0.15 주기 이하로 줄였다. (2) Mun 극궤도에서는 필요한 탈출 방향
  (Mun의 공전 속도 방향)이 우리 궤도면에서 76° 벗어나 있었다. 이 방향은 Mun 궤도 한 바퀴에 두 번(1.8, 5.0, 8.2,
  11.4, 14.6일) 맞춰지는데, 창은 14.8일에 왔다. (3) `transfer_planet`은 SOI 경계에서의 속도를 맞추는데, SOI가 작으면
  그건 v_inf가 아니다(Mun은 2μ/r_SOI = 53,600 m²/s²로 v_inf²와 비슷하다). 계획은 원지점 31,773 km, 경사 23°로
  나와서 태우지 않았다. 궤도를 400 km로 올려(117 + 90 m/s) 14.2일 대기를 빠르게 워프하고, 159 m/s 시드에서 최근접
  튜닝을 돌려 161 m/s로 Minmus 근지점 21.5 km, 경사 80°를 만들었다. 도착 v_inf가 233이라 포획에 약 100이 아니라

## 7.15 Minmus Lab 1: Minmus 극궤도의 과학 정거장
과학을 한 번 따고 끝내는 대신, 계속 벌어 주는 장치를 올렸다. 이동식 과학 실험실(MPL-LG-2)은 실험 데이터를 넣어
두면 시간이 지나면서 과학점수로 바꿔 준다. 이걸 Minmus 14 km 극궤도에 두고 과학자 Bob과 Gwenbro를 태웠다.

- **도구 먼저**: KspBot에 실험실 조작을 넣었다. 상태 보기, 처리 결과 미리 계산(결과 창과 같은 식), 시작, 정지,
  전송, 청소다. CLI로는 `ksp lab status|dry|process|start|stop|transmit|clean`이다.
- **기체**: 도킹 포트(Clamp-O-Tron), OKTO, Science Jr, 배터리 Z-1k 3개, 반작용휠, MPL-LG-2, C7 어댑터 탱크(goo 2,

- **발사대 EVA 시험이 두 번 사람을 죽였다**(둘 다 revert): 커발이 MPL 해치에 나타나는 순간 기체 전체가 한 번
  걷어차인다. 0.5초 만에 기울기 0 → 3.6°, 속도 1 m/s가 생겼고, 87 t 로켓이 발사대 위로 쓰러졌다. 해치 1 m 안에
  다른 부품의 충돌체가 있는지 보는 `eva check`를 만들었지만, 이 기체에는 겹치는 부품이 없었다(이제 겹치면 EVA
  자체를 거부한다). 저궤도에서 재 보니 MPL에서 EVA를 하면 떠 있는 정거장에 약 6°/s, 0.08 m/s가 더해진다(평소

  나간" 사고도 같은 발길질이었을 가능성이 크다. 이 발길질은 궤도도 바꾼다. 원지점 속도가 7.5 m/s뿐인 긴 타원
  궤도에서는 EVA 한 번이 근지점을 14 km에서 −5.5 km로 떨어뜨렸고, 바이옴 투어의 EVA 9번은 13×15 km 궤도를
  7.8×15 km로 만들었다.

## 7.16 계약 혼선: 동기궤도 계약을 받으려다 Ike 정거장을 받다 (Keo Relay 3)
- **엉뚱한 계약**: 동기궤도 중계 계약을 `accept "keosynchronous"`로 받았다. 수락은 됐는데 바로 이어진 저장이
  NRE(NullReferenceException)를 던졌고, CLI는 ERROR를 찍었다. 실패한 줄 알고 `accept 4`로 다시 받았는데, 그사이
  목록 순서가 밀려서 **"Ike 궤도에 새 정거장 건설"** 계약이 수락됐다. 이어진 장면 전환은 옛 세이브를 반쯤 다시
  읽었다. 자금이 1.368M으로 돌아갔고, 계약 객체는 "진행 중"인데 제안 목록에 끼어 있었고, accept()를 불러도 아무
  일도 없었다. `load-save`로는 안 풀렸고 KSP를 재시작하니 풀렸다. 두 계약 모두 다시 제안 상태였고, 잃은 것은 없었다.
  원인은 다음 절(7.17)에서 밝혀진다.
- **그래서 둘 다 받았다**: 이번엔 일부러 동기궤도 계약(48.5k + 124k)과 **Ike 정거장**을 함께 받았다. Ike 정거장은

  재시도하지 않고 경고만 한다.
- **Keo Relay 3**: Keo Relay 2(7.9에서 궤도를 역행으로 뒤집었던 그 기체)에서 goo를 중력계 GRAVMAX로 바꿨다(30.3k).

  82.6×87.7 km(경사 3.94°). `match-orbit`이 궤도면 12.9, 근지점 쪽 647(예상 643~647), 원지점 쪽 457 m/s를 썼고,
  결과는 장반경 3461.7 km, 이심률 0.0567, 경사 4.24°, LAN 95.67°, 근점 인수 299.73°. 이번에는 숫자가 예상대로
  나왔다. **계약 완료**, 자금 1.72 → 1.81M, 과학 146 → 154. 하나 고친 것: `--plan`이 첫 분사의 1 m/s 미만짜리
  미세 보정마다 멈춰서, 이제 2 m/s 미만 보정은 건너뛴다. Keo Relay 3에는 4617 m/s가 남아 예비 중계기나 예인선으로 쓸 수 있다.

  NRE). 이날 비행 → 우주센터 전환 6번 중 2번이었다. 사용자는 "먼저 원인을 찾고, 고칠 필요가 있을 때만 고쳐라"라고
  했다. fable이 Unity 로그와 디컴파일한 KSP/kRPC 코드로 진단했고(`docs/save-nre-diagnosis.md`), opus가 고쳤다.
  - **깃발 하나가 남는다**: KSP에는 "비행 장면이 준비됐고 조종 중인 기체가 있다"는 뜻의 전역 깃발
    (`FlightGlobals.ready`)이 있다. 장면 전환을 요청하면 이 깃발이 내려간다. 그런데 비행 장면의 물리 갱신은, 조종
    중인 기체가 있으면 깃발을 다시 올린다.
  - **물리 한 스텝이 더 돈다**: Unity는 물리를 20 ms(50 Hz) 단위로 계산한다. 화면 한 프레임이 20 ms보다 오래 걸리면
    그 프레임 안에서 물리 스텝을 여러 번 돌린다. kRPC는 우리 명령을 이 물리 스텝 안에서 실행한다. 그래서 첫 스텝에서
    kRPC가 장면 전환을 요청해 깃발이 내려가도, 같은 프레임에 두 번째 물리 스텝이 있으면 아직 남아 있는 비행 장면이
    깃발을 다시 올린다. 그다음 비행 장면이 치워지면서 조종 중인 기체는 없어지는데, 깃발은 올라간 채로 우주센터로
    넘어간다. 우주센터에는 이 깃발을 내려 주는 코드가 없다. 스톡 게임은 메뉴에서 장면을 바꾸므로(프레임의 물리
    스텝이 다 끝난 뒤) 이 순서에 걸리지 않는다. 워프 직후, 기체가 많을 때(약 49개), 메모리가 빠듯해 Windows가
    느릴 때 잘 걸린다.
  - **증거**: 로그에서 "Scene Change : From FLIGHT to SPACECENTER" 바로 뒤에 "Reference Frame: Rotating"이 찍힌다.
    이 줄은 깃발이 올라가 있을 때 물리 스텝 안에서만 찍힌다. 정상적인 전환 세 번에는 이 줄이 없었다.
  - **왜 저장이 죽나**: 저장 코드는 "깃발이 올라가 있으면 조종 중인 기체의 번호를 적는다". 깃발은 올라가 있는데
    기체는 없으니 NRE가 난다.
  - **왜 경력이 되감기나**: KSP는 저장할 때 비행 상태를 먼저 적고, 그다음에 자금과 계약 같은 메모리 속 스냅샷을
    갱신한다. 비행 상태에서 NRE가 나면 스냅샷은 갱신되지 않는다. 다음 장면 전환은 자금과 계약을 그 낡은 스냅샷에서
    다시 만든다. 그래서 자금이 1.368M으로 돌아가고, 계약이 다시 "제안"이 되고, 시간도 되감겼다. 게다가 kRPC는 계약
    객체를 ID로 캐시해 두기 때문에, 우리 쪽에는 죽은 옛 계약 객체가 돌아왔다. accept()가 아무 일도 안 한 이유다.
    KSP를 재시작하면 캐시가 비지만, `load-save`로는 kRPC 서버가 그대로 살아 있어 안 비었다. 디스크의 세이브가
    망가지지는 않았다. 깨진 동안에는 저장 자체가 한 번도 써지지 않았기 때문이다.
  - **수정**(KspBot + CLI): 비행 밖에서는 매 Update마다 남은 깃발을 내리는 SceneGuard. 절대 예외를 던지지 않고
    ok/error를 돌려주는 `Save` 프로시저를 모든 CLI 저장이 쓰고, 실패하면 명령을 멈춘다. 장면 전환(`SwitchScene`)은
    먼저 저장하고, 물리 스텝이 아닌 Update 단계의 코루틴에서 우주센터나 트래킹 스테이션을 연다. `ksp scene`은 로드를
    기다린 뒤 시험 저장을 해 본다. `recover`는 아직 물리 스텝에서 장면을 바꾸지만, 우주센터에서 가드가 깃발을 고친다.
  - 수정 없이도 되살리는 법은 있었다. 트래킹 스테이션에 갔다가 우주센터로 돌아오면 깃발이 내려간다. 대신 마지막
    정상 저장 이후의 일은 잃는다. 이 방법으로 되살렸다(UT 22,856,293으로 돌아가, 우주센터에서 한 워프만 잃었다).
- **KSP가 다시 안 켜졌다**: 수정을 설치하는 `install.sh`가 세이브를 저장하고 KSP를 껐는데, **KSP가 다시 올라오지
  않았다**. 이날 두 번째다(taskkill 뒤 Steam 실행이 가끔 아무 일도 안 한다). Windows 메모리도 다시 높았다(가용
  5.4 GB, 커밋 20.3 / 33.8 GB, 비페이징 풀 1.81 GB). 사용자가 PC를 재시작했다.

## 7.22 Eve 1 귀환: 게임이 숨긴 조우
7.14에서 fable이 짠 귀환 계획은 출발까지 미터 단위로 맞았다. 문제는 그다음, 게임 화면에 Kerbin 조우가 나오지
않는 것이었다.

- **출발**: `depart Kerbin --pe 30000 --plan`이 원지점에서 궤도면 기울이기 104.6 m/s(예상 105)와 탈출 시험 계산
  215(계획 215)를 냈다. 기울이기를 태우고, 두 번째 `depart ... --at 29029189`로 214.8 m/s를 태워 탈출했다. Eve SOI
  이탈 UT 29,087,752, 태양 원일점 15.96 Gm.
- **조우가 없다**: `correct Kerbin`이 조우를 찾지 못했다(거친 탐색 48 m/s, "no encounter"). 궤도는 UT 약 35,464,577에
  Kerbin을 39 Mm 거리로 지나간다. Kerbin SOI 반지름은 84 Mm다. 최근접 거리를 0.26 Mm까지 줄이는 시험 노드를
  넣어도 Kerbin 궤도 패치가 나오지 않았다.
- **진단(fable)**: 디컴파일한 `PatchedConics._CheckEncounter`와 `Orbit._SolveClosestApproach`를 읽고, 우리
  `kspbot/kepler.py`로 같은 계산을 재현했다. KSP의 조우 계산기는 두 궤도가 교차하는 두 지점 중 첫 번째(+23일,
  거리 308 Mm)에서 탐색을 시작한다. 두 번째 후보 시각은 궤도 주기 P에 대해 (−P/2, P/2] 범위로 접어서 쓰는데,
  두 시각의 차이(4,303,298초)가 P/2보다 10시간 길었다. 그래서 두 번째 후보가 과거로 떨어졌고, 진짜 통과(+73일)는
  한 번도 검사되지 않았다. 중요한 사실이 하나 더 있었다. **SOI 전환은 이 예측과 상관없다.** `OrbitDriver.
  CheckDominantBody`가 실제 위치로 판정한다(레일 워프에서도 1배속에서도). 화면에 안 보일 뿐 기체는 Kerbin SOI에
  들어간다. 그리고 UT가 약 31.2M을 넘어 첫 교차점이 과거가 되면 게임도 조우를 보여 줄 것이라고 예측했다.
- **예측대로 나타났다**: UT 31.2M이 지나자 게임에 Kerbin 조우가 떴다(근지점 약 39 Mm). `correct` 3.6 m/s로 근지점
  28.5 km를 계획했는데 분사 오차로 1,809 km. UT 34.5M에 3.2 m/s를 더 태워 **근지점 30.3 km**(들어오는 길에 Mun
  없음).
- **귀환**: 도착 v_inf 2,126에서 재진입했다(`collect_science`: 새로 옮긴 것 0, 포드에 11개). 드로그는 20 km에서
  771 m/s에 펴졌고, Grasslands에 내렸다. **Jeb 회수, 과학 3,594 → 4,214(+620), 자금 3.61 → 3.64M.** 7.11에서 포드에
  실렸다고 계산한 약 1017점에는 못 미친다.
- **교훈**: 게임 화면에 조우가 없다고 조우가 없는 것은 아니다. 게임의 예측기도 버그가 있을 수 있고, 이번에는 우리
  쪽의 독립된 궤도 계산(`kepler.py`)이 그걸 가려냈다. 고치려고 분사하는 대신 기다리는 게 답이었다.

## 8. 모드화 후보
지금 만든 KspBot 모드에서 떼어 내 독립 모드로 낼 만한 것:
1. **JSON → craft 빌더** (`CraftBuilder.cs`): 텍스트 명세로 기체를 조립한다. 스택 노드, 표면 부착, 대칭,
   스테이징, rigid/autostrut를 지원한다. LLM이나 스크립트로 기체를 설계할 때 쓸 수 있다.
2. **kRPC 커리어 확장 서비스** (`Service.cs`): 기술 연구, 시설 업그레이드, 고용, KSP 비행 이벤트 로그 스트림.
   kRPC에 없는 커리어 조작 API.
3. **세이브 자동 로드** (`AutoLoad.cs`): 헤드리스 또는 자동화 실행용.
4. (Python) **비행 기록기**: KSP 비행 로그와 텔레메트리를 합쳐 이상 징후 경보를 낸다.
5. 팝업 닫기(`DismissDialogs`)와 비행 이벤트 로그(`FlightEvents`)는 이 프로젝트에만 쓰이는 기능이 아니다.
   kRPC로 KSP를 자동화하는 사람이라면 누구나 쓸 만한 작은 유틸리티다.

앞으로 필요할 수 있는 것: EVA 조작(kRPC에 없음: EVA 나가기, 깃발 꽂기, 표본 채취, 탑승), 스트럿 부품 배치(조립기 확장).
